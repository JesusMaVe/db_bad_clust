1. Resumen Ejecutivo

El sistema actual es un motor de reglas determinista que detecta 10 categorias de anti-patrones en esquemas Oracle. No usa ML para la clasificacion final: los embeddings BERT se calculan pero no se consumen, y Random Forest / One-Class SVM fueron descartados.

El motor alcanza accuracy 89.3% y F1-macro 84.7% contra ground truth manual, usando exclusivamente metadata de Oracle: tipos de dato, constraints, nombres de columnas.

Actual

  • Rule engine determinista (Python puro)
  • SBERT calculado pero no consumido
  • ML descartado (RF: F1=0.17, SVM: 83% FP)

Futuro

  • SBERT como feature del rule engine
  • GNN como clasificador paralelo
  • Ensemble: rule engine + GNN + SBERT

2. Arquitectura

rule_engine.py (1611 lineas) contiene tres componentes:

  • ColumnRuleEngine — 8 reglas de columna + 4 report-level
  • TableRuleEngine — 4 reglas de tabla + 6 report-level
  • classify() — Funcion unificada de merge

3. Reglas de Columna (8 activas)

wrong_date_as_text confianza: 0.90

Columna con nombre sugiriendo fecha pero tipo VARCHAR2 o CHAR.

fecha date time created updated nacimiento alta baja

Ejemplo: CLIENTES_DIRECCIONES.FECHA_REGISTRO es VARCHAR2 → detectado.

wrong_number_as_text confianza: 0.85

Columna con nombre sugiriendo numero pero tipo VARCHAR2 o CHAR.

precio costo salario monto total amount balance saldo
self_contradictory confianza: 0.80

Columna booleana almacenada como VARCHAR2 o CHAR.

flag active activo enabled is_active es_activo

Patrones de prefijo: es_*, is_*, has_*, tiene_*, puede_*

reserved_words confianza: 0.95

Nombre de columna es exactamente una palabra reservada SQL (91 palabras). Match exacto, case-sensitive.

self_referencing confianza: 0.95 / 0.70

FK que referencia la misma tabla. Nombres tipicos: parent_id, manager_id, ref_*

impossible_data confianza: 0.95

Columna en PK que permite NULL, o FK que referencia columna inexistente. Solo existe en benchmark sintetico.

polymorphic confianza: 0.75

Columna con nombre de discriminador de tipo o patron _O_. Nombres: type, tipo, discriminador, class

wrong_data_types confianza: 0.85

Tabla con >20% de columnas VARCHAR2 con keywords de fecha/numero. Trigger: columnas detectadas como number_as_text o date_as_text.

4. Reglas de Tabla (4 activas)

giant_table umbral: 15 columnas

Todas las columnas heredan el label. Excepcion: columnas polymorphic preservan su label.

eav_pattern

Tabla con entity_id + columna tipo attribute + columna tipo value.

inconsistent_naming

Mezcla espanol/ingles o predominio de genericos: id, name, value, description, code

wrong_data_types

Tabla donde >20% de columnas VARCHAR2 tienen keywords de fecha/numero.

Por que funciona:

  1. Los anti-patrones son estructurales, no semanticos. Un VARCHAR2 que deberia ser DATE se detecta por tipo + keyword.
  2. La metadata de Oracle es suficiente. PK, FK, Unique, data_length dan toda la senal.
  3. Las reglas son interpretables. Cada deteccion genera explanation + fix.
  4. Determinismo = reproducibilidad. Sin varianza de modelo.

8. GNN — Propuesta Futura

Cero codigo actual. Una mencion en el reporte de estado como prioridad media.

Los anti-patrones son relaciones entre entidades, no solo propiedades individuales:

  • wrong_data_types → relacion nombre-tipo
  • eav_pattern → relacion entre 3 columnas
  • self_referencing → FK consigo misma

Arquitectura propuesta

Grafo Schema → GCN 64 → GCN 32 → Readout → Clasificador 10

Ventajas vs Limitaciones

Ventajas

  • Captura relaciones automaticamente
  • Puede descubrir nuevos patrones

Limitaciones

  • Dataset pequeno (243 columnas)
  • Overfitting casi garantizado
  • +200MB de dependencias
Cuando el proyecto escale a +1000 tablas con ground truth acumulado y multiples SGBDs, el GNN tendra sentido.
